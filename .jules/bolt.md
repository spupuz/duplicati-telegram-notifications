## 2024-05-18 - Deferring Bash String Manipulations in Loops
**Learning:** Native Bash `while read` loops are extremely slow for parsing large text files. Relying solely on early exits (e.g., `[[ -z "$val" ]] && continue`) is insufficient if the file contains a massive number of unparseable lines. Always pre-filter the input using a highly optimized C binary like `grep` via process substitution (e.g., `while read ...; done < <(grep ":" "$FILE")`) before feeding it to the Bash loop to significantly reduce CPU overhead. Also, place an early exit (short-circuit) condition for invalid structures at the very top of the loop to skip expensive native Bash string manipulations on log lines that do not match the expected structure, yielding significant CPU savings.
**Action:** Always place early exit (short-circuit) conditions at the very top of scripts and loops before any environment loading, parsing, or network requests to prevent redundant overhead on skipped operations. Specifically in Bash loops, validate structure *before* processing values.

## 2024-09-17 - Strict grep pre-filtering for read loops
**Learning:** Even when using `grep` to pre-filter input for a `while read` loop, you must make the `grep` pattern as strict as possible (e.g. matching the *exact* expected variable structure) to avoid flooding bash with unparseable log lines like timestamped entries. A generic `grep ":"` still lets thousands of irrelevant lines into the slow bash loop.
**Action:** Always pre-filter loop inputs with the most restrictive regex possible in C-binaries like `grep` to completely shield native bash string manipulation from irrelevant log output.
