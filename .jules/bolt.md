## 2024-08-28 - Avoid micro-optimizations in network-bound, infrequent scripts
**Learning:** Optimizing bash fork/exec overhead (like replacing `dirname`, `basename`, or `tr` with native parameter expansions) in a script whose execution time is entirely dominated by network latency (e.g., `curl` requests) is a classic premature micro-optimization. Furthermore, replacing `source <(...)` with a line-by-line `while read` loop breaks multi-line string environment variables. In the context of a post-backup script that runs infrequently, shaving off ~5ms has zero measurable real-world impact and introduces unnecessary risk and regressions.
**Action:** Always evaluate the architectural context of the script before optimizing. If the script is network-bound and runs infrequently, focus on network-level performance (if applicable) or leave the code alone to maintain readability and correctness. Do not sacrifice robust, standard bash constructs for negligible performance gains.
